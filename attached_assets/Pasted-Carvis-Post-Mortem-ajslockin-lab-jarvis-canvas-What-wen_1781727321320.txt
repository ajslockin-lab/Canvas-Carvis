Carvis Post-Mortem — ajslockin-lab/jarvis-canvas

What went right


The leaked Canvas OAuth token from the earlier commit is genuinely gone — git history was rewritten, the old commit object no longer exists, the token string doesn't appear anywhere in the repo or its history anymore.
The orb visual is a real, original implementation (artifacts/jarvis-canvas/src/lib/carvisOrb.ts, 412 lines of plain Three.js — particle buffer geometry, AnalyserNode hookup, idle/listening/thinking/speaking states). Not copied from anything. This is exactly the "design" piece we wanted ported cleanly.
No hardcoded secrets in the current working tree itself — what's left is all in history, not in the live files.


P0 — fix today, before anyone else looks at this repo


A real production secret is in git history. Commit 225082a ("Fix: auto-generate and set ENCRYPTION_KEY env var") hardcoded the actual AES-256-GCM key — the one encrypting every user's stored Canvas token — into .replit's [userenv.shared] block, and pushed it to the public repo. It's no longer in the current file, but the value is permanently recoverable from history. This is more serious than the original OAuth token leak: it's the key that protects everyone's stored data, not one token.

Rotate it: generate a new 32-byte key and store it in Replit's actual Secrets pane (the lock icon in the sidebar), not in .replit itself. .replit's [userenv] section is tracked by git — anything written there gets committed.
Heads up: rotating it means any Canvas tokens already encrypted with the old key become undecipherable. Users (i.e., you, testing it) will need to re-link/re-authenticate Canvas after the rotation.
Scrub the old key value from history the same way the OAuth token was handled (git filter-repo + force-push).



Confirm the original Canvas OAuth token was actually revoked in Canvas's account settings (Approved Integrations). The history rewrite cleaned the repo, but if that token was never revoked at the source, it's still a live, usable credential — the repo cleanup doesn't invalidate it by itself.
Stop using .replit's [userenv] block for secrets going forward. It's committed to git by default. Use Replit Secrets for anything sensitive from here on.


P1 — fix before calling this "done" / before showing it as a portfolio piece


Still no LICENSE file anywhere in the repo, despite the README implying an open project. Add a real LICENSE (MIT) at the root.
Rebrand is half-done. The README says "CARVIS" but the actual code still says "jarvis" everywhere: the app folder is artifacts/jarvis-canvas, the package name is @workspace/jarvis-canvas, the Postgres DB defaults to jarvis, and there's a separate companion repo literally named pwajarvismobile. Looks inconsistent to anyone who opens the file tree, even though the UI itself says Carvis.
The Chrome extension only works against localhost:20034 (host_permissions in manifest.json). As shipped, it can't talk to anything except your own dev machine — nobody else can actually install and use it. Needs the real deployed backend URL added before this is demo-able.
There's a fourth repo now in scope that wasn't part of the original plan: ajslockin-lab/pwajarvismobile, referenced in the README as the companion mobile PWA. Worth deciding explicitly: is that part of "the portfolio piece" too, or is this repo self-contained and the mobile PWA is a separate, later thing?
